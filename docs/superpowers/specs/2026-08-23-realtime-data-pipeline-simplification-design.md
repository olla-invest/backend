# 실시간 데이터 파이프라인 단순화 설계

## 1. 목적

실시간차트와 이슈테마 API의 엔드포인트, 요청 형식, 응답 스키마를 변경하지 않으면서 다음 문제를 해결한다.

- 동일 종목이 API 또는 호출 시점에 따라 실시간가와 전일 종가를 불규칙하게 반환하는 문제
- 실시간 구독 대상, 실시간차트 노출 대상, 이슈테마 노출 대상이 달라 발생하는 실시간 데이터 공백
- 5분 RS 캐시, 10분 장중 순위 스냅샷, 일별 확정 순위의 역할이 혼재된 구조
- 현재 화면 순위와 최근 3일 순위 이력이 서로 다른 과정에서 만들어지지만 구분이 불명확한 문제
- API마다 실시간가 유효성 검사와 종가 폴백을 중복 구현한 문제

## 2. 호환성 원칙

다음 외부 계약은 유지한다.

- 모든 API URL과 HTTP method
- query parameter와 request body
- 응답 필드명, 타입, 중첩 구조
- 실시간 데이터가 없을 때 일별 종가를 반환하는 기존 동작

`priceSource`, `fallbackReason`, `observedAt` 등의 신규 응답 필드는 추가하지 않는다. 데이터 출처와 폴백 사유는 내부 로그와 진단 정보로만 관리한다.

## 3. 현재 구조의 문제

### 3.1 가격 결정 로직 중복

실시간차트와 이슈테마가 각각 다음 판단을 구현하고 있다.

- 현재 장 운영시간인지
- 실시간 체결값이 오늘 수신된 값인지
- 마지막 체결 이후 10분이 지나지 않았는지
- 유효한 실시간값이 없을 때 어떤 DB 가격으로 폴백할지

중복 구현 때문에 API별 경계 시각과 가격 출처가 달라질 수 있다.

### 3.2 구독 여부와 가격 수신 여부 혼용

구독 성공은 체결값 수신을 보장하지 않는다. 현재 구조는 구독 목록과 가격 캐시를 같은 서비스에서 관리하며, 구독 성공 후 첫 체결이 오지 않은 상태와 정상 수신 상태를 명확히 분리하지 않는다.

또한 서버 시작 시 일괄 구독은 최신 정적 필터 통과 종목 중 최대 200개로 제한된다. 나머지는 실시간차트 페이지 또는 상세차트 조회 시 비동기로 구독된다. 이슈테마 조회는 추가 구독을 수행하지 않는다.

### 3.3 순위 데이터의 책임 혼재

- `rank`: 일별 RS 계산 결과
- `currentRank`: 장중 동적 필터 또는 마감 확정 결과
- `displayRank`: API 요청 시 필터와 정렬을 적용한 화면 위치
- `stock_current_rank_snapshots`: 10분 단위 장중 순위

최근 3일 이력은 일별 `current_rank`를 읽지만 현재 순위는 요청 시 재계산될 수 있다. 일별 확정 단계가 누락되면 현재 화면에는 종목이 있어도 과거 이력은 `null`이 된다.

### 3.4 캐시 역할 혼재

5분 캐시는 구간 RS 및 커스텀 RS 계산 결과용이다. 실시간 가격과 장중 순위에는 관여하지 않지만, 현재 구조에서는 갱신 주기가 비슷해 하나의 실시간 집계 체계처럼 보인다. 캐시의 역할과 무효화 조건을 코드 경계로 분리할 필요가 있다.

## 4. 목표 구조

### 4.1 공통 현재가 결정기

내부 전용 `CurrentPriceResolver`를 도입한다. 모든 API는 이 컴포넌트를 통해 표시 가격을 결정한다.

입력:

- 종목 코드
- 실시간 가격 후보
- 일별 지표 종가 또는 최신 저장 종가
- 판단 기준 시각

내부 결과:

- 선택된 가격
- 실시간 데이터 사용 여부
- 내부 폴백 사유

외부 API에는 기존 숫자 필드만 전달한다.

가격 선택 규칙은 다음 순서를 따른다.

1. 현재가 KRX 장중인지 확인한다.
2. 실시간 체결값이 현재 KST 거래일에 수신됐는지 확인한다.
3. 마지막 수신 후 10분 이내인지 확인한다.
4. 가격이 유한한 양수인지 확인한다.
5. 모두 만족하면 실시간가를 사용한다.
6. 그렇지 않으면 해당 API가 기존에 사용하던 일별 지표 종가를 사용한다.
7. 일별 지표 종가도 없으면 기존 API의 최종 기본값을 유지한다.

이 규칙은 가격뿐 아니라 등락률 계산에서 실시간 데이터를 사용할지 판단하는 기준에도 동일하게 적용한다.

### 4.2 실시간 상태와 구독 상태 분리

`RealtimePriceCacheService`는 수신한 최신 체결값만 관리한다. 구독 요청과 성공 여부는 별도의 구독 관리자 책임으로 이동한다.

구독 관리자는 다음 상태를 구분한다.

- 구독 필요
- 구독 요청 중
- 구독 성공
- 구독 실패 및 재시도 대기

체결 캐시는 구독 성공 여부와 무관하게 실제로 수신한 데이터만 저장한다. 가격 결정기는 구독 상태가 아니라 체결값의 시각과 값만 보고 실시간 유효성을 판단한다.

초기 단계에서는 저장소를 인메모리로 유지한다. Redis 전환은 외부 동작을 바꾸지 않는 별도 후속 단계로 분리한다. 이를 통해 이번 변경에서 인프라 변경과 로직 변경을 동시에 수행하지 않는다.

### 4.3 구독 후보 통합

구독 대상은 다음 집합의 합집합으로 만든다.

- 최신 정적 필터 통과 종목
- 현재 이슈테마 데이터에 포함되는 종목
- API 호출로 명시적으로 요청된 실시간차트 페이지 및 상세 종목

중복 종목은 제거하고 기존 키움 배치 크기에 맞춰 구독한다. 구독 가능 수는 설정값으로 관리하고, 키움의 실제 동시 등록 한도가 검증되기 전에는 현재 운영 한도를 유지한다. 후보가 한도를 넘으면 상세차트 활성 종목, 현재 API 페이지 종목, 이슈테마 상세 노출 종목, 랭킹 종목, 나머지 이슈테마 종목 순으로 선택한다. 이에 따라 사용자가 실제로 보고 있는 종목을 기존의 고정 상위 200개보다 우선한다.

구독 동기화는 다음 시점에 수행한다.

- 서버 실시간 연결 준비 완료 후
- 일별 메트릭 계산 완료 후
- 이슈테마 스냅샷 또는 매핑 갱신 완료 후
- 페이지 및 상세 종목 조회 시 누락 종목 보완

API 요청은 구독 완료를 기다리지 않는다. 따라서 응답 시간은 유지하며, 첫 호출에서는 기존처럼 종가가 반환될 수 있다. 이후 체결 수신부터 공통 가격 결정기가 실시간가를 사용한다.

### 4.4 순위 책임 분리

각 데이터의 내부 의미를 다음과 같이 고정한다.

- 일별 `rank`: 일별 RS 배치 순위
- 장중 스냅샷 `current_rank`: 해당 10분 시점의 동적 필터 통과 순위
- 일별 `current_rank`: 해당 거래일의 마감 확정 순위
- `displayRank`: API 응답을 위한 요청 시점 표시 순위

외부 응답 필드명은 유지하되 내부 변수와 함수명은 위 의미에 맞게 변경한다.

최근 3일 `rankHistory`는 계속 일별 마감 확정 `current_rank`만 사용한다. 마감 확정은 다음 순서로 실행한다.

1. 당일 종가 캔들 수집 완료
2. 당일 일별 메트릭 계산 완료
3. 당일 마지막 유효 장중 스냅샷 선택
4. 당일 일별 메트릭에 마감 순위 반영
5. 반영 건수 및 완료 상태 기록

장중 스냅샷은 직전 확정 거래일의 정적 지표와 당일 실시간 가격을 조합할 수 있다. 이때 스냅샷 거래일은 실제 장중 거래일이며, 로그에 정적 지표 기준일을 별도로 기록한다.

마감 확정 단계에서는 당일 스냅샷과 당일 메트릭만 결합한다. 당일 스냅샷이 없으면 전일 메트릭으로 만든 임시 스냅샷을 확정값으로 사용하지 않고, 당일 종가와 당일 메트릭을 기준으로 마감용 순위를 새로 계산한다. 확정 작업은 같은 거래일에 재실행해도 동일 결과가 되도록 만든다.

### 4.5 캐시 역할 제한

캐시는 다음 책임만 가진다.

- 종목 기본 목록 캐시: 키움 종목 마스터 호출 절감
- 구간 RS 캐시: 동일 조건 RS 재계산 방지
- 커스텀 RS 캐시: 동일 기간과 가중치 재계산 방지

캐시는 다음 데이터의 정합성을 결정하지 않는다.

- 표시 현재가
- 실시간 구독 성공 여부
- 10분 장중 순위
- 일별 마감 확정 순위
- 최근 3일 순위 이력

RS 캐시 키는 데이터 기준 거래일과 계산 조건을 계속 포함한다. 가격 또는 장중 스냅샷 갱신을 이유로 RS 캐시를 임의 무효화하지 않는다.

### 4.6 이슈테마와 실시간차트 기준

기존 제품 동작을 유지한다.

- 이슈테마는 최신 지표의 RS 점수가 0보다 큰 테마 매핑 종목을 사용한다.
- 실시간차트는 정적 필터와 동적 필터를 통과한 종목을 사용한다.

두 화면의 종목 집합을 강제로 같게 만들지 않는다. 대신 이슈테마 종목을 실시간 구독 후보에 포함해, 기준 차이 때문에 실시간 가격까지 누락되는 문제만 제거한다.

## 5. 컴포넌트 변경

### 5.1 신규 내부 컴포넌트

`CurrentPriceResolver`

- 장 운영시간 및 데이터 신선도 판단
- 실시간가와 DB 종가 선택
- 실시간 등락률 사용 여부 통일
- 순수 함수 중심으로 구성해 시각별 단위 테스트 가능

`RealtimeSubscriptionManager`

- 구독 후보 합집합 생성
- 구독 상태 및 재시도 관리
- 키움 배치 요청 수행
- 연결 복구 후 재동기화

### 5.2 기존 컴포넌트 역할 축소

`RealtimePriceCacheService`

- 최신 체결값 저장과 조회만 담당
- 구독 목록과 구독 성공 이벤트 처리 제거

`RealTimeChartService`

- 직접 가격 유효성 검사 제거
- 공통 가격 결정기 사용
- 구독 세부 구현 제거
- API 응답 조립과 차트 계산에 집중

`IssueThemeService`

- 직접 실시간가 유효성 검사 제거
- 공통 가격 결정기 사용
- 테마 노출 종목을 구독 후보로 전달

`CurrentRankService`

- 장중 스냅샷 생성과 마감 확정을 명확히 분리
- 장중 스냅샷의 거래일과 정적 지표 기준일을 구분
- 마감 확정 시 당일 스냅샷과 당일 메트릭 일치 검증
- 마감 확정의 재실행 가능성 보장

`DataSchedulerService`

- 종가 수집, 메트릭 계산, 마감 순위 확정 순서를 명시적으로 실행
- 각 단계 실패 시 후속 단계를 진행하지 않음
- 기존 Redis 분산락과 실행 기록 유지

## 6. 오류 처리와 관측성

외부 응답은 유지하되 내부 로그를 구조화한다.

- 실시간 폴백 건수와 원인별 집계
- 구독 후보 수, 요청 수, 성공 수, 실패 수
- 체결값 보유 종목 수와 신선한 체결값 보유 종목 수
- 10분 스냅샷 전체 행 수와 순위 부여 행 수
- 마감 확정 대상 수와 반영 수
- 스냅샷 거래일과 메트릭 거래일 불일치

종목별 로그는 장애 조사 시에만 debug 수준으로 남기고, 일반 운영 로그는 집계값 중심으로 기록한다.

구독 실패는 기존 재시도 횟수와 백오프를 유지한다. 재시도 소진 후에도 다음 구독 동기화 시점에는 다시 후보로 평가할 수 있어야 한다.

## 7. 테스트 전략

### 7.1 가격 결정 단위 테스트

- 장중의 신선한 실시간가 사용
- 10분 초과 실시간가 거부
- 다른 KST 거래일 데이터 거부
- 장 종료 후 종가 사용
- 0, 음수, NaN 실시간가 거부
- 실시간가 부재 시 기존 종가 폴백

### 7.2 구독 관리자 단위 테스트

- 여러 출처의 후보 합집합과 중복 제거
- 성공한 종목의 중복 요청 방지
- 실패한 종목 재시도
- 연결 복구 시 전체 재동기화
- 배치 크기 분할

### 7.3 순위 집계 테스트

- 당일 메트릭 생성 후 마감 순위 확정
- 당일 스냅샷이 없을 때 당일 데이터로 생성
- 전일 스냅샷을 당일 순위로 사용하지 않음
- 동일 거래일 재실행 결과 동일
- 최근 3일 중 일부 종목이 순위 밖이면 해당 날짜만 `null`

### 7.4 API 계약 회귀 테스트

- 실시간차트 목록, 상세, 검색 응답 스냅샷 비교
- 이슈테마 목록과 상세 응답 스냅샷 비교
- 모든 기존 응답 필드와 타입 유지
- 실시간값 존재 및 부재 상황에서 기존 폴백 형태 유지

## 8. 단계별 적용

### 1단계: 가격 판단 통합

- `CurrentPriceResolver` 추가
- 실시간차트와 이슈테마의 중복 판단을 교체
- API 계약 회귀 테스트 추가

### 2단계: 구독 관리 통합

- `RealtimeSubscriptionManager` 추가
- 가격 캐시에서 구독 상태 제거
- 실시간차트와 이슈테마 후보 합집합 적용

### 3단계: 순위 집계 정리

- 장중 스냅샷과 마감 확정 함수 분리
- 스케줄러 실행 순서 수정
- 재실행 및 부분 실패 테스트 추가

### 4단계: 중복 제거 및 운영 검증

- 기존 가격 검사, 구독 보조 상태, 중복 폴백 코드 제거
- 운영 로그와 캐시 통계 검증
- 인바디, 하나금융지주를 포함한 문제 종목을 대상으로 실시간 수신 및 최근 3일 순위 확인

Redis 기반 실시간 가격 공유는 다중 서버 배포에서 인스턴스별 체결 캐시 차이가 실제로 확인될 경우 별도 단계로 진행한다. 이번 작업에는 포함하지 않는다.

## 9. 완료 기준

- 기존 엔드포인트와 응답 스키마가 변경되지 않는다.
- 실시간차트와 이슈테마가 동일한 실시간 데이터 유효성 규칙을 사용한다.
- 이슈테마 노출 종목이 구독 후보에서 누락되지 않는다.
- 5분 RS 캐시는 가격과 순위 집계에 영향을 주지 않는다.
- 장중 10분 스냅샷과 일별 마감 순위의 역할이 코드와 테스트에서 분리된다.
- 최근 3일 순위는 거래일별 마감 확정 결과와 일치한다.
- 구독 실패, 가격 폴백, 마감 확정 누락을 운영 로그에서 구분할 수 있다.
